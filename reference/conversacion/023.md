Sí, pero hasta ahora la tenemos considerada más como **multi-agent delegation** que como una capa formal de **Agent-to-Agent Communication**. Para una arquitectura empresarial, yo la elevaría a first-class component.

La distinguiría de tres cosas que ya tenemos: `ActivationLayer` inicia ejecuciones, `WorkflowRuntime` coordina pasos, y `ToolRuntime` ejecuta capabilities. La comunicación entre agentes necesita un contrato propio porque un agente puede pedir trabajo, delegar contexto, recibir resultados, rechazar una tarea, reportar progreso o escalar.

Conceptualmente:

```text
Agent A
   │
   │ AgentMessageEnvelope
   ▼
Agent Communication Layer
   │
   ├── routing
   ├── identity
   ├── authorization
   ├── correlation
   ├── delivery semantics
   ├── context boundaries
   └── audit
   │
   ▼
Agent B
```

No permitiría que un agente invoque directamente métodos internos de otro agente. Debe existir un **Agent Communication Bus / Agent Gateway**.

El contrato mínimo podría ser:

```text
STRUCT AgentEnvelope
    messageId: MessageId

    fromAgent: AgentId
    toAgent: AgentId

    type: AgentMessageType

    taskId: Optional<TaskId>
    correlationId: CorrelationId
    causationId: Optional<MessageId>

    payload: Value

    contextRefs: List<ContextRef>
    artifactRefs: List<ArtifactRef>

    constraints: ExecutionConstraints

    createdAt: Timestamp
    expiresAt: Optional<Timestamp>
END
```

Y los tipos de mensaje no deberían limitarse a texto:

```text
ENUM AgentMessageType
    TASK_REQUEST
    TASK_ACCEPTED
    TASK_REJECTED
    PROGRESS
    RESULT
    FAILURE
    QUESTION
    CONTEXT_REQUEST
    CONTEXT_RESPONSE
    CANCEL
    ESCALATION
END
```

Por ejemplo, una delegación:

```text
SupervisorAgent
       │
       │ TASK_REQUEST
       │
       ▼
ResearchAgent

"Analyze vendor X"

constraints:
    maxCost = $1.00
    deadline = 5 min
    allowedCapabilities = [...]
```

Después:

```text
ResearchAgent
       │
       ├── TASK_ACCEPTED
       │
       ├── PROGRESS
       │
       └── RESULT
               │
               ▼
        SupervisorAgent
```

Esto es mejor que compartir la conversación completa entre agentes.

La regla que pondría en la Constitution sería:

> **Agents communicate through explicit contracts, not shared implicit state.**

Y otra:

> **Context delegation must be intentional and bounded.**

No haría:

```text
Agent A memory
      =
Agent B memory
```

Sino:

```text
Agent A
   │
   │ delegates:
   │ - task
   │ - selected context
   │ - constraints
   ▼
Agent B
```

Eso evita contaminación de contexto, problemas de seguridad y crecimiento incontrolado de tokens.

También necesitamos distinguir **delegación síncrona y asíncrona**.

Síncrona:

```text
Agent A
  ↓
request Agent B
  ↓
wait
  ↓
result
```

Sirve para tareas cortas.

Asíncrona:

```text
Agent A
  ↓
TASK_REQUEST
  ↓
Queue
  ↓
Agent B
  ↓
...
  ↓
RESULT EVENT
  ↓
Agent A resumes
```

Mucho más apropiado para enterprise.

Y aquí reutilizamos casi toda la infraestructura que ya definimos:

```text
Agent-to-Agent Communication

uses:

Identity
PolicyEngine
Activation Layer
Messaging
Durable Execution
Execution Ledger
Artifact Store
Context Layer
Budgets
Observability
```

Por ejemplo, `Agent B` no debería heredar automáticamente los permisos de `Agent A`.

Necesitamos delegación explícita:

```text
Agent A
    permissions:
        customer.read
        refund.propose

delegates to Agent B:
        customer.read
```

No:

```text
Agent B gets everything Agent A can do
```

Así que entraría también el concepto de:

```text
DelegationToken
```

Algo como:

```text
STRUCT DelegationToken
    issuer: AgentId
    subject: AgentId

    capabilities: List<CapabilityId>

    scope: ResourceScope

    validUntil: Timestamp

    parentExecution: RunId
END
```

Eso nos permite construir chains seguras:

```text
Human
  ↓ authority
Supervisor Agent
  ↓ delegated subset
Research Agent
  ↓ delegated subset
Database Capability
```

Y queda trazable.

Otro componente importante sería el **Agent Directory / Agent Registry**, que ya mencionamos. Para comunicación, debe permitir descubrir agentes por capability, no necesariamente por nombre:

```text
Agent A asks:

"I need capability:
legal.contract.review"

        ↓

Agent Registry

        ↓

LegalReviewAgent v3
```

Entonces:

```text
Agent A
  ↓
Capability Request
  ↓
Agent Registry
  ↓
Agent Communication Layer
  ↓
Agent B
```

Eso evita hardcodear:

```text
callLegalAgent()
```

También agregaría semántica de **result contracts**.

Un agente delegado no debe devolver simplemente:

```text
"Done."
```

Debe tener:

```text
STRUCT AgentTaskResult
    taskId: TaskId
    status: TaskStatus

    output: Value

    evidence: List<ArtifactRef>

    assumptions: List<Text>

    unresolvedIssues: List<Text>

    confidence: Optional<Score>

    usage: ExecutionUsage
END
```

Esto es clave para que el agente superior pueda evaluar el resultado.

Para multi-agent, además necesitamos prevenir ciclos:

```text
Agent A
 ↓
Agent B
 ↓
Agent C
 ↓
Agent A
 ↓
...
```

Por eso `ExecutionController` debería controlar:

```text
maxDelegationDepth
maxChildAgents
maxTotalRuns
maxDelegationCost
```

Ejemplo:

```text
ExecutionBudget
├── maxTurns = 30
├── maxToolCalls = 80
├── maxDelegationDepth = 3
├── maxChildRuns = 10
└── maxCost = $5
```

Y la topología debería quedar observable:

```text
Parent Run R1
│
├── Child Run R2 — ResearchAgent
│
├── Child Run R3 — DataAgent
│    └── Child Run R5 — SQLAgent
│
└── Child Run R4 — ReviewerAgent
```

Eso forma un:

```text
Execution Graph
```

Más que una simple session.

Yo agregaría entonces formalmente estos componentes a nuestra arquitectura:

```text
AgentCommunicationGateway
AgentRegistry
DelegationManager
ExecutionGraph
```

y los contratos:

```text
AgentEnvelope
AgentTaskRequest
AgentTaskResult
DelegationToken
AgentCommunicationPolicy
```

Dentro del mapa enterprise:

```text
                    AGENT RUNTIME
                         │
             ┌───────────┴───────────┐
             ▼                       ▼
          Agent A                  Agent B
             │                       ▲
             │                       │
             └── AgentCommunication ─┘
                       Layer
                         │
               ┌─────────┼─────────┐
               ▼         ▼         ▼
             Policy   Registry   Messaging
               │         │         │
               └─────────┼─────────┘
                         ▼
                 Execution Graph
```

Así que la respuesta es: **sí, estaba contemplado, pero todavía no suficientemente formalizado**. Yo lo añadiría como un plano explícito porque, una vez que tienes muchos agentes empresariales, la comunicación, delegación de autoridad, límites de contexto y trazabilidad entre ellos se convierten en problemas arquitectónicos propios.
