Cuando las llamadas son independientes se pueden realizar en paralelo, pero hay actividades que para iniciar la ejecución requieren el resultado del paso previo 

Exactamente.

La regla conceptual es:

> **Paralelizar cuando no existe dependencia de datos ni de estado. Secuencializar cuando una acción depende del resultado o del efecto de otra.**

Por ejemplo, esto es perfectamente paralelizable:

```text
read(auth.ts) ───────┐
read(user.ts) ───────┼──► juntar resultados ──► modelo
read(config.ts) ─────┘
```

Porque ninguna lectura necesita conocer el resultado de las otras.

Pero esto no:

```text
write(config.ts)
      ↓
npm test
      ↓
read(test-output)
```

`npm test` necesita que el `write` haya terminado, y el análisis del resultado necesita que el test exista.

Hay además una segunda razón más sutil: **side effects**. Dos operaciones podrían no depender explícitamente una de otra y aun así ser peligrosas en paralelo:

```text
git checkout branch-a
git commit ...
```

o:

```text
database migration
deploy application
```

Comparten estado del entorno. Por eso el harness necesita distinguir entre:

```text
Dependency
      +
Shared mutable state
      +
Side effects
```

Esto nos lleva a una idea arquitectónica interesante para nuestro harness. Una herramienta no debería definirse solamente por `name`, `schema` y `execute`. Podríamos añadir metadata operacional:

```ts
interface Tool {
  name: string;
  description: string;
  schema: JSONSchema;

  execution: {
    mode: "parallel" | "sequential";
    sideEffect: "none" | "local" | "external";
  };

  execute(input: unknown): Promise<unknown>;
}
```

Después podremos enriquecerlo:

```ts
execution: {
  mode: "sequential",
  sideEffect: "external",
  risk: "high",
  requiresApproval: true
}
```

Y fíjate cómo empieza a aparecer nuestro **enterprise harness** casi naturalmente:

```text
Tool Definition
     │
     ├── Schema
     ├── Execution mode
     ├── Side effects
     ├── Risk
     ├── Permissions
     └── Approval
```

No estamos metiendo estas reglas en el prompt. **Son propiedades determinísticas del runtime.**

Y ahora viene probablemente uno de los conceptos más importantes de Pi que quiero que entendamos antes de diseñar nuestro código: **event-driven architecture**.

Pi podría simplemente hacer:

```ts
const result = await tool.execute();
```

pero en cambio genera eventos como:

```text
tool_execution_start
tool_execution_update
tool_execution_end
```

y lo mismo ocurre con mensajes, turns y la ejecución completa.

Pi básicamente transforma esto:

```text
Agent Loop
```

en esto:

```text
                 ┌── UI
                 │
                 ├── Logger
                 │
Agent Loop ─events── Telemetry
                 │
                 ├── Session
                 │
                 ├── Audit
                 │
                 └── Extensions
```

La siguiente pregunta es importante porque esta decisión arquitectónica va a afectar casi todo lo que construyamos:

**¿Qué ventaja crees que tiene que `agent-loop` emita eventos y que UI, logging, persistencia, telemetry, etc. escuchen esos eventos, en lugar de que el propio `agent-loop` llame directamente a cada uno de esos componentes?**
