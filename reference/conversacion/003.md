Sí. Revisé la arquitectura actual del repositorio oficial de Pi. La primera corrección importante respecto a lo que te expliqué antes es esta:

> **Pi no empieza desde `coding-agent`. Empieza desde un núcleo de tres capas: `ai → agent-core → coding-agent`.**

El repositorio actual está en `earendil-works/pi` y el monorepo separa explícitamente `pi-ai`, `pi-agent-core`, `pi-coding-agent`, `pi-tui` y ahora también telemetría. ([GitHub][1])

### 1. La arquitectura real

```text
┌────────────────────────────────────────────┐
│             pi-coding-agent                │
│                                            │
│ CLI · Sessions · Context · Skills          │
│ Extensions · Tools · Compaction · UI       │
└──────────────────┬─────────────────────────┘
                   │
                   ▼
┌────────────────────────────────────────────┐
│              pi-agent-core                 │
│                                            │
│ Agent · State · Agent Loop · Tool Calls    │
│ Events · Steering · Follow-up              │
└──────────────────┬─────────────────────────┘
                   │
                   ▼
┌────────────────────────────────────────────┐
│                  pi-ai                     │
│                                            │
│ Models · Providers · Messages · Streaming  │
│ OpenAI · Anthropic · Google · etc.         │
└────────────────────────────────────────────┘
```

El detalle fundamental es que **`agent-core` no sabe que está construyendo código**. Es un runtime genérico para agentes. El comportamiento de coding agent aparece en la capa superior. ([GitHub][2])

Eso es exactamente una idea que deberíamos copiar.

## 2. El verdadero corazón: `agent-loop.ts`

Este archivo es probablemente el primero que deberíamos estudiar juntos.

Tiene unas 700 líneas de implementación y hace bastante más que el pseudocódigo básico que vimos antes. ([GitHub][3])

Su flujo conceptual es:

```text
Prompt
   │
   ▼
AgentContext
   │
   ▼
transformContext()
   │
   ▼
convertToLlm()
   │
   ▼
LLM streaming
   │
   ▼
Assistant Message
   │
   ├── no tool calls ───────► terminar
   │
   └── tool calls
          │
          ▼
     validate args
          │
          ▼
     beforeToolCall()
          │
          ▼
       execute()
          │
          ▼
      afterToolCall()
          │
          ▼
     ToolResultMessage
          │
          └──────────────► nuevo turno
```

Hay una decisión arquitectónica muy buena aquí:

> Pi trabaja internamente con `AgentMessage[]` y solamente los convierte al formato particular del LLM **en el boundary de llamada al modelo**. ([GitHub][3])

Eso significa:

```text
Nuestra aplicación
     ↓
AgentMessage

NO

OpenAIMessage
AnthropicMessage
GoogleMessage
```

Solo en el último momento:

```text
AgentMessage[]
       ↓
convertToLlm()
       ↓
Provider-specific messages
```

Esto desacopla completamente el agente del proveedor.

## 3. Otra cosa que Pi hace mejor de lo que parecía: eventos

El loop no simplemente devuelve texto.

Emite eventos.

Por ejemplo:

```text
agent_start
turn_start

message_start
message_update
message_end

tool_execution_start
tool_execution_update
tool_execution_end

turn_end
agent_end
```

El sistema entero puede observar esos eventos. ([GitHub][3])

Eso permite que otras capas hagan:

```text
Agent Loop
   │
   ├──► TUI
   ├──► Logs
   ├──► Session persistence
   ├──► Telemetry
   ├──► Approval system
   ├──► Observability
   └──► External API
```

sin introducir lógica de UI dentro del agente.

**Esta es probablemente una de las decisiones que más vale copiar.**

# 4. El agente no controla las sesiones

Otra separación importante.

`Agent` mantiene un estado operativo:

```text
AgentState
├── messages
├── model
├── thinkingLevel
├── systemPrompt
├── tools
├── streamingMessage
└── errorMessage
```

([GitHub][4])

Pero el coding agent tiene otra capa:

```text
SessionManager
```

que se encarga de persistencia, branching y recuperación.

Pi guarda las sesiones automáticamente y permite:

```text
session
 │
 ├── message
 ├── message
 ├── tool result
 │
 ├──────── branch A
 │          ├── ...
 │
 └──────── branch B
            ├── ...
```

No piensa la conversación solamente como una lista lineal. ([GitHub][5])

Aquí hay otra lección para nosotros:

> **Agent state ≠ persistent session state.**

Son problemas diferentes.

# 5. Pi empieza con solo cuatro herramientas

Esto también me parece muy importante para nuestro proyecto.

Por defecto el coding agent recibe:

```text
read
write
edit
bash
```

Hay algunas herramientas read-only adicionales disponibles, pero estas cuatro constituyen el conjunto básico. ([GitHub][6])

Fíjate lo poderoso de esto:

```text
LLM
 │
 ├─ read
 ├─ write
 ├─ edit
 └─ bash
```

Con `bash`, indirectamente tienes acceso a:

```text
git
npm
grep
find
curl
python
docker
gh
terraform
kubectl
...
```

Por eso Pi deliberadamente no convierte cada capacidad en una herramienta del LLM.

Eso reduce muchísimo el tool surface.

# 6. Context engineering en Pi es bastante sencillo

Pi carga instrucciones de:

```text
~/.pi/agent/AGENTS.md

parent/
    AGENTS.md

project/
    AGENTS.md
```

y también permite:

```text
SYSTEM.md
APPEND_SYSTEM.md
```

([GitHub][7])

Además tiene compaction cuando el contexto se acerca al límite.

La idea no es construir inicialmente un gigantesco RAG engine.

Es:

```text
System Prompt
      +
Project Instructions
      +
Skills relevantes
      +
Conversation
      +
Tool Results
```

Después agrega compaction.

Esto me hace cambiar ligeramente mi recomendación anterior para nuestro v0.1:

**no construiría todavía un `context-engine` sofisticado.**

Primero implementaría exactamente este patrón.

# 7. Skills y Extensions son dos cosas completamente diferentes

Esto también es clave.

### Skill

Es conocimiento/instrucciones:

```text
skills/
  debugging/
     SKILL.md
```

Ejemplo conceptual:

```markdown
# Debugging

When debugging:

1. Reproduce the problem.
2. Inspect logs.
3. Form a hypothesis.
4. Verify it.
5. Apply the smallest fix.
```

El agente lo consume como contexto. ([GitHub][8])

### Extension

Es **código TypeScript ejecutable**:

```ts
export default function(pi) {

    pi.registerTool(...);

    pi.registerCommand(...);

    pi.on("tool_call", ...);

}
```

Una extensión puede introducir herramientas, comandos, UI, hooks, interceptar eventos y almacenar estado. ([GitHub][9])

Por tanto:

```text
Skill
    = enseñar al agente

Extension
    = modificar el harness
```

Muy buena separación conceptual.

# 8. Hay otro detalle muy interesante: Hooks alrededor de tools

El `agent-loop` soporta algo equivalente a:

```ts
beforeToolCall(...)
```

y:

```ts
afterToolCall(...)
```

([GitHub][3])

Esto significa que puedes construir encima del mismo runtime:

```text
LLM requests deploy()
        │
        ▼
 beforeToolCall
        │
        ├─ Security
        ├─ Validation
        ├─ Approval
        ├─ Audit
        └─ Transformation
        │
        ▼
     execute
        │
        ▼
 afterToolCall
```

Pi no incluye una gran permission architecture de fábrica. De hecho, explícitamente advierte que corre con los permisos del proceso y recomienda aislamiento/contenedores cuando se requieren fronteras más fuertes. ([GitHub][1])

Pero **la arquitectura del loop permite introducir nuestra capa enterprise ahí**.

Eso sería una diferencia importante entre Pi y lo que nosotros construiríamos.

# 9. Pi soporta parallel tool execution

Esto tampoco lo había enfatizado antes.

Si el modelo genera:

```text
read(a.ts)
read(b.ts)
read(c.ts)
```

pueden ejecutarse en paralelo.

Pero una herramienta puede marcar:

```text
executionMode: "sequential"
```

y el loop respeta esa restricción. ([GitHub][3])

Conceptualmente:

```text
Tool calls
   │
   ├── read(a) ─┐
   ├── read(b) ─┼── parallel
   └── read(c) ─┘

vs.

migration()
    ↓
deploy()
    ↓
test()

sequential
```

Eso conviene copiar desde el principio porque la abstracción es pequeña.

# 10. Steering messages

Esta parte me parece particularmente elegante.

Mientras el agente está trabajando, el usuario puede mandar otro mensaje.

Pi distingue:

```text
Steering
```

de

```text
Follow-up
```

Steering entra después del turno actual y puede cambiar la dirección del agente.

Follow-up espera hasta que el trabajo actual termine. ([GitHub][7])

Así:

```text
USER:
Refactor authentication.

AGENT:
reading...
editing...

USER:
Don't change the public API.
        ↓
      steering
        ↓
Agent receives instruction
before continuing.
```

Esta capacidad hace que el agente sea realmente interactivo y no simplemente:

```text
prompt()
await 90 seconds
response
```

# 11. La filosofía arquitectónica que veo ahora

Después de revisar el repo, resumiría Pi así:

```text
                ┌─────────────┐
                │     LLM     │
                └──────┬──────┘
                       │
                 provider API
                       │
                ┌──────▼──────┐
                │    pi-ai    │
                └──────┬──────┘
                       │
                 AgentMessage
                       │
             ┌─────────▼─────────┐
             │    agent-core     │
             │                   │
             │ loop              │
             │ tools             │
             │ state             │
             │ events            │
             └─────────┬─────────┘
                       │
           ┌───────────▼────────────┐
           │     coding-agent       │
           │                        │
           │ sessions               │
           │ context                │
           │ skills                 │
           │ extensions             │
           │ compaction             │
           │ CLI / TUI              │
           └───────────┬────────────┘
                       │
                       ▼
                     USER
```

Y su principio central parece ser:

> **Mantener el runtime pequeño y convertir las funcionalidades en extensiones de primitives simples.**

La propia documentación lo describe como **“primitives, not features”**. ([Pi][10])

# Lo que yo copiaría

Después de esta primera revisión, copiaría conceptualmente estas siete cosas:

```text
1. Monorepo separado:
   ai / agent / application

2. AgentMessage independiente del proveedor.

3. Event-driven agent loop.

4. Tool interface extremadamente pequeña.

5. beforeToolCall / afterToolCall hooks.

6. Agent state separado de Session state.

7. Skills ≠ Extensions.
```

Y **no copiaría exactamente** una cosa:

```text
Pi
Tools → OS permissions
```

Para enterprise construiría:

```text
Tool Request
    ↓
Policy
    ↓
Identity
    ↓
Authorization
    ↓
Sandbox
    ↓
Execution
    ↓
Audit
```

Pi deliberadamente deja esa frontera fuera del core. ([GitHub][1])
