Y si el harness es para programar aplicaciones? Cómo sería? Quiero tener varios ejemplos a la mano

Sí. De hecho conviene tener **varios “reference harnesses” por dominio** porque eso muestra qué primitives son comunes y qué cambia según el tipo de trabajo.

Para un harness orientado a **programar aplicaciones**, la arquitectura base sería la misma, pero cambiarían principalmente los agentes, skills, tools, policies y validators.

Un ejemplo de alto nivel sería:

```text
                    APPLICATION DEV HARNESS
                              │
                    ┌─────────┴─────────┐
                    │                   │
              Project Controller    Project State
                    │
                    ▼
              Development Pipeline
                    │
        ┌───────────┼────────────┐
        ▼           ▼            ▼
   Planning      Coding       Validation
        │           │            │
        └───────────┼────────────┘
                    ▼
                Quality Gates
                    │
                    ▼
             Repository Changes
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
        Tests      Build      PR
```

Aquí el **source of truth** ya no sería el libro, sino el repositorio:

```text
repo/
├── src/
├── tests/
├── docs/
├── package.json
├── architecture/
└── ...
```

Y el estado del harness podría ser:

```text
STRUCT ProjectState
    repository: RepositoryState
    branch: BranchRef
    task: DevelopmentTask

    architecture: ArchitectureState
    dependencies: DependencyGraph

    tests: TestState
    build: BuildState

    changes: List<FileChange>
    decisions: List<ADR>
END
```

Los agentes iniciales podrían ser pocos:

```text
Planner Agent
    entiende la tarea
    identifica archivos
    propone plan

Developer Agent
    modifica código

Reviewer Agent
    revisa calidad y arquitectura

Test Agent
    analiza fallas y cobertura
```

Pero yo evitaría comenzar con cuatro agentes separados. En una primera versión, un solo `Developer Agent` puede asumir planning + coding + testing, y luego separar roles cuando exista una razón real.

Los **skills** serían algo como:

```text
skills/
├── inspect-repository/
├── implement-feature/
├── debug-failure/
├── write-unit-tests/
├── review-pull-request/
├── refactor-code/
├── database-migration/
├── frontend-component/
├── api-endpoint/
└── architecture-review/
```

Y las tools mínimas:

```text
read_file
write_file
edit_file
list_files
search_code
shell
git_diff
git_status
```

Después puedes añadir:

```text
github
database
browser
docker
kubernetes
cloud
jira
```

Pero no todas desde el comienzo.

El flujo típico sería:

```text
User Task
   ↓
Understand Requirement
   ↓
Inspect Repository
   ↓
Build Relevant Context
   ↓
Plan Change
   ↓
Edit Files
   ↓
Run Tests
   ↓
Observe Failures
   ↓
Fix
   ↓
Run Build
   ↓
Review Diff
   ↓
Return Result
```

En pseudocódigo:

```text
FUNCTION executeDevelopmentTask(
    task: DevelopmentTask,
    state: ProjectState,
    execution: ExecutionContext
) -> DevelopmentResult

    context: RepositoryContext =
        RepositoryContextEngine.build(
            task,
            state
        )

    WHILE ExecutionController.canContinue()

        response: ModelResponse =
            ModelGateway.generate(
                context,
                execution
            )

        IF response.hasToolCalls()

            results: List<ToolResult> =
                ToolRuntime.execute(
                    response.toolCalls,
                    execution
                )

            context.addObservations(results)

            CONTINUE
        END

        IF ValidationPipeline.isSatisfied(state)
            RETURN DevelopmentResult.success(
                response.output
            )
        END

        context.add(
            ValidationPipeline.feedback(state)
        )

    END

    RETURN DevelopmentResult.incomplete()
END
```

La diferencia importante frente al Book Harness es que aquí los **quality gates** son técnicos:

```text
Formatting
Lint
Type Check
Unit Tests
Integration Tests
Build
Security Scan
Architecture Rules
Git Diff Review
```

Y muchas de esas validaciones deben ser scripts determinísticos, no agentes.

Por ejemplo:

```text
scripts/
├── lint
├── typecheck
├── test
├── build
├── validate-architecture
├── validate-dependencies
├── detect-secrets
└── validate-diff
```

Las policies podrían decir:

```yaml
git:
  commit: allow
  push: require_approval

filesystem:
  repository_write: allow
  outside_repository: deny

deployment:
  development: allow
  staging: require_approval
  production: deny

database:
  read: allow
  schema_change: require_approval
  destructive_change: deny
```

Y aquí HITL aparece naturalmente:

```text
Developer Agent
      ↓
creates migration
      ↓
Policy Engine
      ↓
SCHEMA_CHANGE_REQUIRES_APPROVAL
      ↓
WAITING_FOR_HUMAN
```

Lo interesante es que todos comparten el mismo núcleo:

```text
                    GENERIC HARNESS

ModelGateway
AgentLoop
ContextEngine
ToolRuntime
PolicyEngine
SessionManager
EventBus
ExecutionController
HumanInteraction
Skills
Evals
```

y cada dominio añade:

```text
Domain State
Domain Skills
Domain Tools
Domain Policies
Domain Validators
Domain UI
```

Así puedes pensar el sistema como:

```text
Generic Harness
      +
Domain Pack
      =
Specialized Harness
```

Por ejemplo:

```text
Generic Harness
+
Coding Pack
=
Coding Harness
```

```text
Generic Harness
+
Book Pack
=
Book Harness
```

```text
Generic Harness
+
Research Pack
=
Research Harness
```

Esa separación me parece una de las ideas más fuertes para el libro, porque demuestra que **no estamos construyendo un harness distinto cada vez; estamos construyendo un runtime común con domain packs especializados**.
