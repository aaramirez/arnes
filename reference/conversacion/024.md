A2A?

**A2A es exactamente el estándar que deberíamos considerar** para la capa de comunicación entre agentes que acabamos de describir.

De hecho, yo corregiría una parte de mi propuesta anterior: **no conviene inventar nuestro propio protocolo externo `AgentEnvelope` si A2A cubre esa frontera**. Conviene que nuestra arquitectura tenga contratos internos propios y un **A2A Adapter/Gateway** para interoperabilidad.

A2A (**Agent2Agent Protocol**) es actualmente un estándar abierto, originalmente desarrollado por Google y donado a la Linux Foundation. La versión publicada actual es **1.0.0**. Su objetivo es permitir que sistemas agentic independientes —incluso construidos con frameworks, lenguajes o proveedores diferentes— descubran capacidades, colaboren, manejen tareas y se intercambien información sin compartir su memoria, herramientas o implementación interna. ([GitHub][1])

[Documentación oficial de A2A](https://a2a-protocol.org/latest/?utm_source=chatgpt.com)

### Cómo lo incorporaría a nuestro Harness

No reemplazaría nuestro `AgentCommunicationGateway`. Lo convertiría en una **abstracción independiente del protocolo**:

```text
                 Agent A
                    │
                    ▼
        AgentCommunicationGateway
                    │
          ┌─────────┼──────────┐
          │         │          │
          ▼         ▼          ▼
       Internal    A2A       Future
       Protocol   Adapter    Adapter
          │         │
          ▼         ▼
       Agent B   External Agent
```

Esto mantiene nuestra regla fundamental:

> **El core del Harness no debe acoplarse a protocolos externos.**

Nuestro contrato podría ser:

```text
INTERFACE AgentCommunicationGateway

    discover(
        capability: CapabilityQuery
    ) -> List<AgentDescriptor>

    delegate(
        request: AgentTaskRequest,
        execution: ExecutionContext
    ) -> AgentTaskHandle

    send(
        message: AgentMessage
    ) -> DeliveryResult

    cancel(
        task: AgentTaskHandle
    ) -> CancellationResult

END
```

Y el adapter:

```text
A2AAgentAdapter
    IMPLEMENTS AgentCommunicationGateway
```

De esa manera el `AgentLoop` **no sabe que existe A2A**.

### A2A encaja muy bien con varias cosas que ya diseñamos

Hay una correspondencia interesante:

| Nuestra arquitectura        | A2A                                 |
| --------------------------- | ----------------------------------- |
| `AgentRegistry`             | Agent discovery / Agent Card        |
| `AgentTaskRequest`          | Task / Message                      |
| `AgentTaskResult`           | Task result / Artifacts             |
| `AgentCommunicationGateway` | A2A protocol boundary               |
| `ExecutionGraph`            | Relaciones entre ejecuciones/tareas |
| `ArtifactStore`             | A2A Artifacts                       |
| Durable Execution           | Long-running A2A Tasks              |
| Async communication         | Streaming / asynchronous operations |
| Agent capabilities          | Skills declaradas por el agente     |
| Identity / Authorization    | Enterprise security mechanisms      |

A2A está diseñado precisamente para que los agentes sean **opacos entre sí**: un agente no necesita conocer el prompt, memoria, tools o implementación interna del otro. ([GitHub][2])

Eso coincide muchísimo con nuestra Architecture Constitution:

```text
Agent A
   │
   │ Task + Context + Constraints
   ▼
Agent B

NOT:

Agent A
   │
   ▼
Agent B internal memory
Agent B tools
Agent B prompt
Agent B implementation
```

### Y aclara también A2A vs MCP

Esta separación debería aparecer explícitamente en nuestro libro.

```text
                    AGENT
                      │
           ┌──────────┴──────────┐
           │                     │
           ▼                     ▼
          MCP                   A2A
           │                     │
           ▼                     ▼
     Tools / Data             Agents
```

**MCP**

```text
Agent
  ↓
Tool / Resource
```

**A2A**

```text
Agent
  ↓
Agent
```

La documentación oficial hace exactamente esta distinción: MCP estandariza interacción con herramientas, APIs, datos y recursos; A2A estandariza colaboración entre agentes independientes. Son complementarios. ([GitHub][3])

Y nuestro `ToolRuntime` tampoco debería depender exclusivamente de MCP:

```text
ToolRuntime
     │
 ┌───┴────────────┐
 ▼                ▼
Native         MCP Adapter
Tools
```

Igualmente:

```text
AgentCommunicationGateway
        │
 ┌──────┴────────────┐
 ▼                   ▼
Internal          A2A Adapter
Agents
```

Esto produce una simetría arquitectónica muy limpia.

---

### Pero hay una distinción importante: sub-agents ≠ A2A

Esto es particularmente relevante para nuestro Harness.

La documentación actual de A2A aclara que A2A **no pretende ser el protocolo para que un agente controle sus propios sub-agents internos**. Está orientado a interoperabilidad entre aplicaciones agentic independientes. ([A2A Protocol][4])

Por tanto yo distinguiría:

```text
                  AGENT COMMUNICATION

        ┌────────────────┴────────────────┐
        │                                 │
 Internal Delegation              External Federation
        │                                 │
        ▼                                 ▼
   Sub-Agent Runtime                 A2A Gateway
        │                                 │
        ▼                                 ▼
 Local / Managed Agent        Independent Agent System
```

Ejemplo Coding Harness:

```text
CodingAgent
   │
   ├── internal delegation
   │       ↓
   │   TestAgent
   │
   └── A2A
           ↓
       External Security
       Review Agent
```

No necesitamos pagar el costo operacional de A2A para cada llamada interna entre componentes del mismo runtime.

---

### Esto introduce además el concepto de Agent Federation

Y aquí A2A se vuelve especialmente interesante para enterprise.

Hasta ahora pensábamos:

```text
Enterprise Harness
    ├── SalesAgent
    ├── FinanceAgent
    ├── CodingAgent
    └── NetworkAgent
```

Pero una empresa real eventualmente tendrá:

```text
                    ENTERPRISE AGENT ECOSYSTEM

 Our Harness          Salesforce Agent        SAP Agent
     │                       │                    │
     └────────────── A2A ────┼──────── A2A ─────┘
                             │
                       Partner Agent
```

Ya no controlamos todos los agentes.

Entonces nuestro `AgentRegistry` debería evolucionar hacia algo parecido a:

```text
AgentRegistry
├── Managed Agents
├── Internal Agents
├── External Agents
└── Federated Agents
```

Y A2A proporciona precisamente mecanismos de **discovery y descripción de capacidades** mediante Agent Cards. ([A2A Protocol][5])

### Cambiaría nuestro mapa arquitectónico

Añadiría formalmente:

```text
══════════════════════════════════════════════════════════
               AGENT INTEROPERABILITY PLANE
══════════════════════════════════════════════════════════

AgentCommunicationGateway
        │
        ├── InternalDelegationAdapter
        │
        └── A2AAdapter
                 │
                 ▼
             A2A Protocol
                 │
       ┌─────────┼──────────┐
       ▼         ▼          ▼
    Internal   Partner    Vendor
     Agent      Agent      Agent

Supporting Components:

AgentRegistry
AgentDiscovery
DelegationManager
ExecutionGraph
Identity
Authorization
PolicyEngine
AuditLedger
ContextBoundary
ArtifactStore
```

Y establecería un principio constitucional:

> **Agent interoperability must be protocol-independent at the core and standards-based at external boundaries.**

Con una consecuencia concreta:

```text
Internal contract
        ↓
AgentCommunicationGateway
        ↓
Protocol Adapter
        ↓
A2A
```

No:

```text
AgentLoop
   ↓
A2A SDK
```

Esa diferencia es pequeña visualmente, pero **enorme arquitectónicamente**.

A2A debería, por tanto, aparecer en nuestro libro y Architecture Constitution, pero como **estándar de interoperabilidad en el boundary**, no como dependencia fundamental del Agent Core.
