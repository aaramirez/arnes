How to build a harness like pi?


Assuming you mean **Pi Coding Agent** at pi.dev: yes. A harness like Pi is essentially the runtime around an LLM that controls **context, tools, execution, persistence, permissions, and the agent loop**. Pi deliberately keeps that runtime small and extensible through extensions, skills, prompts, themes, providers, and SDK/RPC modes. ([Pi][1])

For a company-oriented implementation, I would not clone Pi feature-for-feature. I would build a **minimal agent kernel** with this architecture:

```text
┌─────────────────────────────────────────────────────┐

│ CLI │ Web │ API │ Slack │ IDE │ Background Jobs    │

│  └─────┬───────┘   └──────────────┘                │
```

The **core loop can be surprisingly small**. Conceptually:

```ts
while (!done) {
  const context = await contextEngine.build(session);

  const response = await model.generate({
    messages: context.messages,
    tools: toolRegistry.schemas()
  });

  session.append(response);

  if (!response.toolCalls?.length) {
    return response.text;
  }

  for (const call of response.toolCalls) {
    const decision = await policy.authorize(call, session);

    if (!decision.allowed) {
      session.appendToolResult(call.id, {
        error: decision.reason
      });
      continue;
    }

    const result = await toolRegistry.execute(
      call.name,
      call.arguments
    );

    session.appendToolResult(call.id, result);
  }
}
```

But the loop isn't where most of the engineering value lives. The difficult part is the **harness around the loop**.

I would divide your implementation into seven primitives:

1. **Model abstraction.** One internal interface such as `generate()`, with adapters for OpenAI, Anthropic, Gemini, local models, etc. Pi already demonstrates the advantage of making model/provider switching a harness concern rather than hard-wiring the application to one model. ([Pi][1])

2. **Tool registry.** Every capability becomes a strongly typed tool: `read_file`, `write_file`, `shell`, `git`, `search`, `database`, `jira`, `salesforce`, or whatever the company needs. Each tool should expose schema, execution handler, permissions, timeout, audit classification, and side-effect level.

3. **Context engine.** This is arguably more important than the prompt. Don't simply dump conversation history into the model. Build context from layers:

```text
System Constitution
        ↓
Company / Security Policy
        ↓
Agent Role
        ↓
Current Task
        ↓
Relevant Skills
        ↓
Retrieved Business Context
        ↓
Working Memory
        ↓
Recent Interaction History
        ↓
Tool Observations
```

Your context engine should dynamically decide what gets included, summarized, retrieved, discarded, or pinned. That turns **prompt engineering into context engineering**.

4. **Skills.** I particularly like Pi's model here. A skill is not another agent. It is reusable procedural knowledge that tells the agent **how to perform a type of task**. Pi exposes skills alongside extensions and prompt templates. ([Pi][1])

For example:

```text
skills/
  deploy-service/
    SKILL.md

  analyze-incident/
    SKILL.md

  create-rfp/
    SKILL.md

  review-contract/
    SKILL.md
```

A skill might contain:

```markdown
# Analyze Production Incident

## Trigger
Use when investigating a production incident.

## Required context
- Service
- Environment
- Time window

## Procedure
1. Retrieve recent deployments.
2. Retrieve logs.
3. Establish baseline.
4. Correlate first error with deployment/config change.
5. Form hypotheses.
6. Test hypotheses.
7. Return findings and confidence.

## Never
- Modify production.
- Restart services without approval.
```

5. **Extension/plugin runtime.** This is what takes you from a coding agent to a platform. Extensions should be able to register tools, commands, hooks, context providers, policies, lifecycle events, and UI components. Pi explicitly makes extensibility one of its central architectural ideas rather than shipping every possible workflow in the core. ([Pi][1])

I would use something approximately like:

```ts
export interface HarnessExtension {
  name: string;

  setup(api: HarnessAPI): Promise<void>;
}

export interface HarnessAPI {
  tools: ToolRegistry;
  hooks: HookRegistry;
  context: ContextRegistry;
  policies: PolicyRegistry;
  commands: CommandRegistry;
}
```

6. **State and session tree.** Don't treat a session as one giant array of messages. Model it as an event stream:

```text
Session
 ├─ user_message
 ├─ assistant_reasoning_event
 ├─ tool_call
 ├─ tool_result
 ├─ checkpoint
 ├─ context_summary
 └─ branch
```

Pi uses tree-structured/shareable history, which is a strong design choice because agent work naturally branches. ([Pi][1])

7. **Policy layer.** For enterprise use, this becomes mandatory. Tool execution should pass through something like:

```text
READ ONLY
    │
    ▼
LOW-RISK WRITE
    │
    ▼
EXTERNAL SIDE EFFECT
    │
    ▼
CRITICAL ACTION
```

Then apply rules:

```text
read_file                    → automatic
search_database              → automatic
write_source_code            → automatic/sandbox
git_commit                    → automatic
git_push                      → policy-dependent
send_email                    → confirmation
deploy_staging               → policy-dependent
deploy_production            → explicit approval
delete_customer_records      → forbidden
```

This is also why harness design is becoming a security boundary in its own right. Recent work on securing agent harnesses specifically examines sandboxing, skill scanning, and tool restrictions as controls that can be embedded in the harness rather than relying exclusively on model behavior. ([arXiv][2])

One architectural decision I would make differently from many current agent projects is **not starting with multi-agent**. Pi itself intentionally does not make built-in subagents fundamental; subagent behavior can be added later through extensions. ([Pi][1]) There are already Pi packages that implement separate agent processes, parallel delegation, chains, and workspace handoffs on top of those primitives. ([Pi][3])

I would follow:

```text
Level 0
LLM + Prompt
       ↓
Level 1
LLM + Tools
       ↓
Level 2
Context-aware Agent
       ↓
Level 3
Persistent Agent Harness
       ↓
Level 4
Policies + Approvals + Observability
       ↓
Level 5
Automated Workflows
       ↓
Level 6
Multi-Agent Orchestration
```

That's particularly important for **enterprise Generative AI**. Multi-agent architectures often get introduced before companies have solved context quality, tool contracts, authorization, observability, evaluation, or deterministic workflow execution. You end up multiplying an unreliable unit.

So if our goal were to create a **Pi-like harness specifically for enterprise AI**, I would actually make the central abstraction:

> **Agent = Model + Context + Skills + Tools + Policies + State**

and:

> **Harness = the runtime that continuously assembles and governs those six things.**

That gives you something substantially more valuable than another chatbot framework: an **enterprise agent operating layer**.

Given the AI methodology you're developing, there is also a very natural progression here:

```text
Contextualized Multimodal Generation
                ↓
Personalized Interaction
                ↓
Smart Automation
                ↓
Decision + Action + Tools
                ↓
Agent Harness
                ↓
Specialized Agents
                ↓
Enterprise Agent Operating System
```

The harness is essentially the missing technical substrate connecting **automation** to **agents**. Once it exists, individual agents become relatively lightweight configurations instead of independent software projects.
