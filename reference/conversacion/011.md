Hiciste esta pregunta La pregunta para ti sería: ¿por qué crees que conviene que el estado/configuración del agente esté separado de la función que ejecuta el loop, en vez de construir una única clase gigante Agent que haga absolutamente todo? —— El estado tiene información que se puede utilizar para realizar validaciones antes de enviar datos al loop. Se puede moderar lo que entra al loop. Si todo está junto es difícil intervenir en las decisiones que tomará el loop.


Sí. Los 15 principios son una buena base filosófica, pero para convertirlos en una arquitectura implementable yo agregaría **cinco marcos complementarios**: invariantes del sistema, contratos entre componentes, lifecycle del agente, modelo de fallos y criterios de evolución.

Los principios dicen **cómo queremos pensar** el sistema. Lo que falta es definir **qué nunca puede romperse**.

Por ejemplo, estos serían invariantes fuertes:

* ningún tool call se ejecuta sin validación;
* ningún side effect crítico ocurre sin pasar por policy;
* el modelo nunca es fuente de autorización;
* todo tool result vuelve al loop como observación;
* toda ejecución produce eventos auditables;
* el core puede correr sin TUI;
* el core puede correr sin persistencia específica;
* cambiar de proveedor no debe requerir cambios en el agent loop;
* una sesión puede reconstruirse a partir de su estado persistido;
* un error de una tool no debe necesariamente destruir todo el agent run.

Esto es incluso más importante que algunos principios porque permite escribir tests arquitectónicos.

También definiría formalmente los **contratos entre componentes**. Por ejemplo:

```text
AgentLoop
    │
    ├── consumes → AgentState
    ├── consumes → Context
    ├── calls    → ModelProvider
    ├── calls    → ToolRuntime
    └── emits    → AgentEvent
```

El `ToolRuntime` tendría su propio contrato:

```text
ToolRuntime
    │
    ├── receives → ToolCall
    ├── validates
    ├── evaluates policy
    ├── executes
    └── returns → ToolResult
```

Y el Context Engine:

```text
ContextEngine
    │
    ├── AgentConfig
    ├── SessionState
    ├── Skills
    ├── ContextProviders
    └── CurrentTask
          ↓
      ContextSnapshot
```

Esto nos ayuda a evitar dependencias circulares.

Otro aspecto muy importante es definir el **lifecycle completo del agente**. Hasta ahora hemos hablado mucho del loop, pero el loop es solo una parte:

```text
Agent Created
     ↓
Configuration Loaded
     ↓
Session Loaded / Created
     ↓
Context Prepared
     ↓
Agent Run Started
     ↓
┌────────────────────────┐
│       TURN LOOP        │
│                        │
│ Model                  │
│   ↓                    │
│ Decision               │
│   ↓                    │
│ Tool Calls             │
│   ↓                    │
│ Observations           │
│   ↓                    │
│ Model                  │
└────────────────────────┘
     ↓
Completion / Error / Abort
     ↓
State Persisted
     ↓
Agent Run Ended
```

Yo incluso definiría estados explícitos:

```ts
type AgentRunStatus =
  | "created"
  | "running"
  | "waiting_for_tool"
  | "waiting_for_approval"
  | "paused"
  | "completed"
  | "failed"
  | "cancelled";
```

Esto se vuelve crítico cuando agreguemos automatizaciones, approvals y ejecución durable.

También falta algo que considero fundamental: **failure semantics**.

Hay que decidir qué ocurre cuando falla cada capa.

Por ejemplo:

```text
Model timeout
      ↓
retry?

Tool timeout
      ↓
return error observation?

Invalid tool arguments
      ↓
tell model to correct?

Policy denied
      ↓
return denied result?

Context provider unavailable
      ↓
continue degraded?

Session persistence fails
      ↓
stop agent?
```

No todos los errores deben tratarse igual.

Yo usaría una taxonomía:

```text
Recoverable
Transient
Policy
Validation
Tool
Model
Infrastructure
Fatal
```

Por ejemplo:

```text
Tool argument invalid
→ recoverable
→ model puede corregir

HTTP 503
→ transient
→ retry

Tool forbidden
→ policy
→ no retry

Corrupt session
→ infrastructure/fatal
```

Eso convierte el harness en un sistema realmente robusto.

Hay otra dimensión que todavía no hemos tocado suficientemente: **ownership de decisiones**.

Conviene definir claramente quién decide cada cosa:

```text
LLM
decide qué intentar

AgentLoop
decide cuándo continuar el ciclo

ContextEngine
decide qué información mostrar

ToolRuntime
decide cómo ejecutar

PolicyEngine
decide si puede ejecutarse

SessionManager
decide cómo persistir

Scheduler
decide cuándo ejecutar

UI
decide cómo presentar
```

Esta matriz evita uno de los problemas clásicos de frameworks de agentes: que el `Agent` termine tomando todas las decisiones.

También incorporaría desde el principio un concepto que llamaría **Execution Context**.

Algo como:

```ts
interface ExecutionContext {
  runId: string;
  sessionId: string;
  agentId: string;

  user?: UserIdentity;

  environment: "local" | "dev" | "staging" | "prod";

  permissions: PermissionSet;

  abortSignal: AbortSignal;

  traceId: string;
}
```

Ese objeto viaja por:

```text
AgentLoop
 ↓
ToolRuntime
 ↓
Policy
 ↓
Tools
 ↓
Telemetry
```

y mantiene correlacionada toda la ejecución.

Para enterprise es tremendamente útil.

También debemos pensar en **idempotencia**. Si un agente falla después de hacer:

```text
send_invoice()
```

y luego el run se recupera, no queremos:

```text
send_invoice()
send_invoice()
```

dos veces.

Así que para side effects importantes:

```text
Tool Call
    ↓
idempotency key
    ↓
Execution Ledger
    ↓
already executed?
  /             \
yes             no
 ↓               ↓
reuse result    execute
```

Esto se volverá esencial cuando pasemos de coding agents a business agents.

Otra consideración importante es **backpressure y budgets**.

Un agente podría entrar en:

```text
tool
 ↓
model
 ↓
tool
 ↓
model
 ↓
tool
 ↓
...
```

indefinidamente.

El harness debe tener límites:

```ts
maxTurns
maxToolCalls
maxTokens
maxCost
maxRuntime
maxConcurrentTools
```

Por ejemplo:

```yaml
limits:
  maxTurns: 25
  maxToolCalls: 50
  maxRuntimeSeconds: 600
  maxCostUsd: 2.00
```

No debería depender del modelo para decidir cuándo detenerse.

También definiría desde ya **cancelación e interrupción**.

Algo como:

```text
User
 ↓
CANCEL
 ↓
AbortSignal
 ↓
AgentLoop
 ├── cancel model stream
 ├── cancel pending tools
 ├── persist checkpoint
 └── emit agent_cancelled
```

Especialmente si tendremos TUI interactiva.

Y hay otra pieza que para mí debería estar en la arquitectura desde el inicio: **capabilities**, no simplemente tools.

En vez de pensar:

```text
Agent has tool X
```

pensaría:

```text
Agent has capability X
```

Una capability puede resolverse mediante:

```text
Local Tool
MCP Tool
REST API
Remote Agent
Workflow
Human Approval
```

Por ejemplo:

```text
capability:
  customer.lookup
```

podría estar implementado hoy por:

```text
Salesforce API
```

y mañana por:

```text
MCP Salesforce Server
```

El agente no necesita saberlo.

Eso nos lleva a una arquitectura aún más limpia:

```text
Agent
  ↓
Capability
  ↓
Capability Resolver
  ↓
Tool / MCP / API / Agent
```

Y finalmente agregaría un concepto explícito de **Deterministic vs Agentic Execution**.

No todo debe decidirlo el LLM.

```text
Deterministic
─────────────
validation
permissions
routing rules
retries
timeouts
approvals
schemas
budgets

Agentic
─────────────
interpret intent
form hypothesis
select relevant tool
analyze observations
decide next cognitive step
```

Esta separación debería ser uno de los fundamentos más fuertes del sistema:

> **Usar inteligencia probabilística para decisiones semánticas y lógica determinística para control operacional.**

Si juntamos todo lo que hemos descubierto hasta ahora, yo ya no hablaría solamente de los **15 principios**.

Hablaría de un **Architecture Constitution** compuesto por:

```text
Principles
    ↓
Invariants
    ↓
Component Contracts
    ↓
Lifecycle
    ↓
Decision Ownership
    ↓
Failure Semantics
    ↓
Execution Context
    ↓
Security / Policy
    ↓
Budgets / Limits
    ↓
Observability
    ↓
Evolution Rules
```

Y esa constitución debería ser probablemente el documento `ARCHITECTURE.md` principal del proyecto.

De todo lo anterior, los tres conceptos que considero **más importantes añadir ahora mismo** son **invariants**, **decision ownership** y **failure semantics**. Son los que probablemente más nos evitarán errores arquitectónicos cuando empecemos a escribir el core.
