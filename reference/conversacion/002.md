Ok how to star a project like that?


Start **much smaller than the architecture I showed before**. The mistake would be trying to build the enterprise platform on day one. The first goal should be proving one thing:

> **Can we create a reliable agent runtime that receives a task, builds context, calls a model, executes tools, and keeps state?**

I would start the project as a **TypeScript monorepo** and define v0.1 around only five components:

```text
Agent Loop
   +
Model Gateway
   +
Context Builder
   +
Tool Runtime
   +
Session Store
```

Everything else—multi-agent, enterprise integrations, long-term memory, complex permissions, workflows, UI—comes later.

### Phase 1 — Define the contract

Before coding, define the fundamental abstraction:

```ts
export interface Agent {
  id: string;
  model: string;
  systemPrompt: string;
  tools: string[];
}
```

Then define what goes into and comes out of the runtime:

```ts
export interface AgentRequest {
  sessionId: string;
  agentId: string;
  input: string;
}

export interface AgentResponse {
  sessionId: string;
  output: string;
  events: AgentEvent[];
}
```

And most importantly, define events:

```ts
export type AgentEvent =
  | { type: "user_message"; content: string }
  | { type: "assistant_message"; content: string }
  | { type: "tool_call"; tool: string; args: unknown }
  | { type: "tool_result"; tool: string; result: unknown }
  | { type: "error"; message: string };
```

This event model becomes the backbone of the harness.

### Phase 3 — Implement one model only

Do **not** start by supporting five providers.

Start with one.

For example:

```ts
interface ModelProvider {
  generate(request: ModelRequest): Promise<ModelResponse>;
}
```

Then:

```ts
class OpenAIProvider implements ModelProvider {
  async generate(request: ModelRequest) {
    // call model
  }
}
```

The abstraction matters more than multiple implementations.

Later:

```text
ModelProvider
 ├── OpenAIProvider
 ├── AnthropicProvider
 ├── GeminiProvider
 └── LocalProvider
```

But v0.1 only needs one.

### Phase 4 — Build the agent loop

This is the first real milestone.

Something approximately like:

```ts
async function runAgent(
  agent: Agent,
  input: string,
  session: Session
) {
  session.add({
    type: "user_message",
    content: input
  });

  while (true) {
    const context = await buildContext(agent, session);

    const response = await model.generate({
      messages: context.messages,
      tools: toolRegistry.getSchemas(agent.tools)
    });

    if (response.text) {
      session.add({
        type: "assistant_message",
        content: response.text
      });
    }

    if (!response.toolCalls?.length) {
      return response.text;
    }

    for (const toolCall of response.toolCalls) {
      session.add({
        type: "tool_call",
        tool: toolCall.name,
        args: toolCall.args
      });

      const result = await toolRegistry.execute(
        toolCall.name,
        toolCall.args
      );

      session.add({
        type: "tool_result",
        tool: toolCall.name,
        result
      });
    }
  }
}
```

Once that works, **you have an agent harness**.

Everything else is sophistication around this loop.

### Phase 5 — Create only three tools

Don't integrate Jira, Slack, Salesforce, databases and MCP yet.

Start with:

```text
read_file
write_file
shell
```

A tool interface:

```ts
interface Tool<TInput = unknown, TOutput = unknown> {
  name: string;
  description: string;

  schema: unknown;

  execute(input: TInput): Promise<TOutput>;
}
```

Example:

```ts
const readFileTool: Tool = {
  name: "read_file",

  description: "Read a file from the workspace",

  schema: {
    type: "object",
    properties: {
      path: { type: "string" }
    },
    required: ["path"]
  },

  async execute({ path }) {
    return fs.readFile(path, "utf8");
  }
};
```

Then create:

```ts
toolRegistry.register(readFileTool);
toolRegistry.register(writeFileTool);
toolRegistry.register(shellTool);
```

Now your model can act on the environment.

### Phase 6 — Build the context engine

This is where I would start differentiating the platform.

Don't implement:

```ts
messages = entireConversationHistory;
```

Instead:

```ts
const context = [
  systemInstructions,
  agentInstructions,
  relevantProjectContext,
  recentSessionEvents,
  currentUserRequest
];
```

Conceptually:

```text
┌────────────────────────────┐
│ Global System Rules        │
├────────────────────────────┤
│ Agent Definition           │
├────────────────────────────┤
│ Project Context            │
├────────────────────────────┤
│ Relevant Skills            │
├────────────────────────────┤
│ Working Memory             │
├────────────────────────────┤
│ Recent Events              │
├────────────────────────────┤
│ Current Request            │
└────────────────────────────┘
```

Create an interface immediately:

```ts
interface ContextProvider {
  getContext(request: ContextRequest): Promise<ContextBlock[]>;
}
```

That decision will pay off enormously later.

You can eventually plug in:

```text
GitContextProvider
DocumentationProvider
DatabaseContextProvider
UserMemoryProvider
CompanyPolicyProvider
RAGProvider
```

without rewriting your agent.

### Phase 7 — Make agents configuration

Don't hard-code a developer agent.

Create:

```yaml
id: developer

name: Software Developer

model: gpt-5.6

systemPrompt: |
  You are a senior software engineer.
  Inspect the repository before modifying code.
  Prefer minimal changes.
  Test changes whenever possible.

tools:
  - read_file
  - write_file
  - shell
```

Then:

```bash
harness run developer
```

and:

```text
> Fix the failing authentication test.

Agent:
I'll inspect the repository.

→ read_file(package.json)
→ shell("npm test ...")
→ read_file(src/auth.ts)
→ write_file(src/auth.ts)
→ shell("npm test ...")

The authentication issue has been fixed...
```

At that point you have something genuinely useful.

## Your v0.1 target

I would make the acceptance criteria brutally simple.

The harness must be capable of doing this:

```text
$ harness run developer

> Create a simple health endpoint in this project.

Agent
 ↓
Inspect repository
 ↓
Understand framework
 ↓
Read relevant files
 ↓
Modify files
 ↓
Run tests
 ↓
Inspect failures
 ↓
Fix issue
 ↓
Run tests
 ↓
Return result
```

If it can reliably complete that loop, **v0.1 is successful**.

I would not add multi-agent before reaching that point.

## Then v0.2

Once v0.1 works reliably, introduce the first important architectural layer:

```text
                 Agent
                   │
          ┌────────▼────────┐
          │ Policy Engine   │
          └────────┬────────┘
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
      Read       Write      External
    Actions     Actions      Actions
```

For example:

```yaml
permissions:

  read_file:
    policy: allow

  write_file:
    policy: allow

  shell:
    policy: sandbox

  git_push:
    policy: approval

  deploy:
    policy: deny
```

Now you're moving from a coding demo toward an enterprise harness.

## v0.3 — Skills

Then introduce skills:

```text
skills/
├── debug-application/
│   └── SKILL.md
├── review-pull-request/
│   └── SKILL.md
├── create-api/
│   └── SKILL.md
└── investigate-incident/
    └── SKILL.md
```

For example:

```markdown
# Debug Application

## Goal

Identify the root cause before modifying code.

## Procedure

1. Reproduce the issue.
2. Collect relevant logs.
3. Identify the failing boundary.
4. Form a hypothesis.
5. Test the hypothesis.
6. Apply the smallest change.
7. Run regression tests.

## Avoid

- Blindly rewriting modules.
- Changing unrelated code.
- Suppressing errors.
```

Now you're separating:

```text
WHAT YOU ARE
Agent

WHAT YOU CAN DO
Tools

HOW YOU SHOULD DO IT
Skills

WHAT YOU KNOW
Context

WHAT YOU MAY DO
Policies
```

That separation is extremely important.

## v0.4 — Enterprise context

This is where the project starts becoming more interesting than a Pi clone.

Add a context registry:

```text
Company
├── Architecture
├── Engineering standards
├── Processes
├── Products
├── Customers
├── Policies
├── Projects
└── People / Roles
```

Then the agent runtime selects context dynamically:

```text
User:
"Why is checkout failing?"

            ↓

Context Engine

            ↓

Relevant context selected:

+ checkout architecture
+ payments service
+ recent deployments
+ incident history
+ coding standards
+ repository state
+ current logs
```

Not:

```text
"Here are 50,000 tokens of company documentation."
```

That's the difference between **RAG bolted onto a chatbot** and genuine **context engineering**.

Once the single-agent harness is reliable, you can introduce:

```text

 │
 ├─────────────┐
 ▼             ▼
Developer    Researcher
 │             │
 └──────┬──────┘
        ▼
      Reviewer
        │
        ▼

```

But internally they're all just:

```text

```

The multi-agent system therefore becomes an **orchestration problem**, rather than creating an entirely different architecture.

There is one thing I would do **before writing much code**, though: create a small architectural manifesto for the project containing about 8–10 principles.

For example:

```text
1. Context is a first-class architectural component.

2. Tools are explicit capabilities, not prompt tricks.

3. Every action generates an observable event.

4. Side effects pass through policy.

5. Agents are configuration over a shared runtime.

6. Skills contain reusable procedural knowledge.

7. Single-agent reliability precedes multi-agent complexity.

8. The model is replaceable.

9. The harness owns state—not the model.

10. Automation and agents use the same execution substrate.
```

That document will prevent the architecture from turning into a collection of AI features.

If I were starting the actual project, I would make **v0.1 a real runnable repository now** with `README.md`, architecture docs, TypeScript monorepo, CLI, agent loop, model interface, tool registry, `read_file/write_file/shell`, session persistence, one `developer` agent, and a small eval suite. That's enough code to establish the architecture without prematurely building the platform.
