El core corre independientemente y los eventos son procesados para producir efectos secundarios en otros componentes que complementan al core pero no forman parte del mismo como un TUI

Exactamente. Eso es **desacoplamiento por eventos**.

El `core` hace una sola cosa: ejecutar correctamente el ciclo del agente. No necesita saber si existe TUI, API, auditoría, telemetría o almacenamiento.

```text
Agent Core
   │
   ├── agent_start
   ├── turn_start
   ├── message_update
   ├── tool_execution_start
   ├── tool_execution_end
   └── agent_end
          │
          ▼
      Event Bus
          │
   ┌──────┼──────────┬───────────┐
   ▼      ▼          ▼           ▼
  TUI   Logger    Session DB   Telemetry
```

Eso nos da varias ventajas importantes: podemos cambiar la interfaz sin tocar el core, agregar observabilidad sin contaminar el loop, persistir sesiones con otro backend y correr el mismo agente en CLI, web, API o incluso como worker.

Pero hay una distinción arquitectónica que quiero que mantengamos muy clara:

> **No todo debería resolverse mediante eventos.**

Por ejemplo, `telemetry` sí puede escuchar:

```text
tool_execution_end
```

después de que ocurrió.

Pero una política de seguridad que debe impedir una acción **no puede limitarse a escuchar un evento después**:

```text
tool_execution_start
      ↓
observer
      ↓
"esto no estaba permitido"
```

Ya sería tarde.

Para eso necesitamos un mecanismo síncrono dentro del camino crítico:

```text
LLM tool call
     ↓
validation
     ↓
beforeToolCall hook
     ↓
policy decision
     ↓
ALLOW / DENY
     ↓
execute
     ↓
event: tool_execution_end
```

Entonces aparecen dos mecanismos distintos:

```text
EVENTS
“Algo ocurrió”

HOOKS
“Algo está por ocurrir;
puedes intervenir”
```

Ese patrón es muy importante para nuestro harness enterprise.

Por ejemplo:

```text
Events
────────────────────
UI updates
logging
metrics
tracing
session persistence
analytics


Hooks / Middleware
────────────────────
authorization
approval
schema validation
rate limiting
redaction
sandboxing
policy enforcement
```

Y aquí ya tenemos una primera arquitectura bastante sólida del runtime:

```text
                   User
                     │
                     ▼
              ┌─────────────┐
              │ Agent Core  │
              │             │
              │ Agent Loop  │
              └──────┬──────┘
                     │
            Model Request / Response
                     │
                     ▼
               Model Gateway
                     │
                     ▼
                  Model

Tool call returned
       │
       ▼
┌──────────────────────┐
│ Tool Execution Path  │
├──────────────────────┤
│ validate             │
│ hooks                │
│ policy               │
│ execute              │
└──────────┬───────────┘
           │
           ▼
      Tool result
           │
           └──────────► Agent Loop

Meanwhile...

Agent Core
    │
    └── events
          │
   ┌──────┼───────┬─────────┐
   ▼      ▼       ▼         ▼
  UI   Session  Audit    Telemetry
```

Ese dibujo ya se parece mucho más a lo que yo construiría como base real.

La siguiente pieza de Pi que estudiaría es **la separación entre `Agent` y `AgentLoop`**. Parece una diferencia pequeña, pero tiene bastante impacto.

Pi puede pensar aproximadamente así:

```text
Agent
 ├── state
 ├── model
 ├── tools
 ├── configuration
 └── lifecycle

AgentLoop
 └── ejecuta un ciclo usando ese estado
```

La pregunta para ti sería: **¿por qué crees que conviene que el estado/configuración del agente esté separado de la función que ejecuta el loop, en vez de construir una única clase gigante `Agent` que haga absolutamente todo?**
