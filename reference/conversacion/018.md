ADRs?

Sí. **ADR = Architecture Decision Record**.

Es una pieza importante porque la **Architecture Constitution define las reglas**, mientras que los ADR documentan **las decisiones concretas que tomamos dentro de esas reglas**.

Por ejemplo:

```text
Architecture Constitution
        │
        │ establece
        ▼
"El modelo debe ser reemplazable"
        │
        │ obliga a decidir
        ▼
¿Cómo desacoplamos los providers?
        │
        ▼
ADR-0001
"Use ModelGateway + Provider Adapters"
```

Un ADR no debería ser un documento enorme. Normalmente es una decisión arquitectónica, su contexto y sus consecuencias.

En nuestro harness podríamos tener:

```text
docs/
├── ARCHITECTURE_CONSTITUTION.md
│
└── adr/
    ├── ADR-0001-model-provider-abstraction.md
    ├── ADR-0002-agent-state-separation.md
    ├── ADR-0003-event-driven-core.md
    ├── ADR-0004-tool-runtime-boundary.md
    ├── ADR-0005-policy-engine.md
    ├── ADR-0006-human-interaction-runtime.md
    └── ADR-0007-durable-execution.md
```

### Ejemplo: ADR-0002

```markdown
# ADR-0002 — Separate Agent State from Agent Loop

Status: Accepted

## Context

The harness requires the ability to inspect, validate,
transform and persist agent state independently from
the execution mechanism.

A monolithic Agent class would couple state,
configuration and execution.

## Decision

AgentState will be represented independently from
AgentLoop.

AgentLoop receives the state required to execute
a turn but does not own its persistence.

## Rationale

This allows:

- pre-execution validation
- state inspection
- testing
- persistence
- checkpointing
- policy intervention
- alternative execution environments

## Alternatives Considered

### Monolithic Agent class

Rejected because state and execution would become
strongly coupled.

### Stateful AgentLoop

Rejected because persistence and lifecycle concerns
would leak into the execution engine.

## Consequences

Positive:

- easier testing
- explicit lifecycle
- durable execution becomes possible
- easier policy intervention

Negative:

- additional interfaces
- state transitions must be explicitly managed

## Constitutional Impact

Principles:
- P-08 Agent state and session state are different concerns
- P-10 Harness owns execution state

Invariants:
- INV-08 Harness owns execution state
- INV-12 AgentState and SessionState remain independent
```

Lo importante es que meses después, cuando alguien pregunte:

> “¿Por qué no metemos `AgentState` directamente dentro de `AgentLoop` y simplificamos esto?”

no dependamos de recordar esta conversación.

Podemos responder:

```text
Read ADR-0002.
```

Y hay otra propiedad importante: **los ADR no deberían borrarse cuando una decisión cambia**.

Por ejemplo:

```text
ADR-0004
Tool Registry
Status: Superseded

        ↓ replaced by

ADR-0017
Capability Registry
Status: Accepted
```

Así obtenemos una historia de cómo evolucionó la arquitectura:

```text
Constitution
     │
     │ permanent architectural rules
     ▼
ADRs
     │
     │ historical architectural decisions
     ▼
Architecture
     │
     ▼
Code
```

En nuestro proyecto tienen mucho sentido porque ya hemos tomado varias decisiones que merecen ADR propio: separar `AgentState` del loop, core event-driven, TUI fuera del core, model abstraction, ToolRuntime como único execution boundary, HITL independiente de interfaces, ejecución paralela solo cuando no existen dependencias, deterministic vs agentic boundary, durable execution y eventualmente Capability Registry.

De hecho, **antes de empezar a escribir código**, yo crearía aproximadamente **8–10 ADR iniciales** con las decisiones que ya hemos tomado. Eso convertiría nuestras conversaciones de diseño en decisiones arquitectónicas formales y versionadas.
