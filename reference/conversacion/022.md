Hay algo que quiero considerar que todos los métodos que activan el Hartness en general colas API web Books eventos de qué manera el harness se activa en un entorno empresarial no solamente a través de un usuario que escribe instrucciones cuánto cobran


Exactamente. Eso debería convertirse en una **pieza arquitectónica de primer nivel del Generic Harness**. Hasta ahora hemos modelado demasiado el inicio como:

```text
User → Prompt → Harness
```

Eso sirve para un coding assistant, pero **no representa un harness empresarial**.

En una empresa, el harness debería poder ser activado por humanos, sistemas, eventos, schedules, colas, APIs, cambios de estado, webhooks, otros agentes, etc.

Yo lo modelaría como una capa explícita: **Activation Layer** o **Ingress Layer**.

```text
                    ENTERPRISE WORLD

                     ▼

                     │
                     ▼
             Activation Request
                     │
                     ▼
            Admission Controller
                     │
                     ▼
```

Y hay una separación conceptual importante:

El `AgentLoop` no debería contener:

```text

if API...
if queue...
if user...
```

Todo se normaliza antes.

## Y esto cambia nuestra arquitectura

```text
CMP-XXX ActivationGateway
```

Con responsabilidades distintas.

Normaliza mecanismos externos.

```text
INTERFACE ActivationGateway

    receive(
        externalTrigger: ExternalTrigger
    ) -> ActivationRequest

END
```

### AdmissionController

Decide si puede entrar.

```text
INTERFACE AdmissionController

    evaluate(
        activation: ActivationRequest,
        system: SystemState
    ) -> AdmissionDecision

END
```

### ActivationRouter

Decide quién debe procesarlo.

```text
INTERFACE ActivationRouter

    route(
        activation: ActivationRequest
    ) -> ExecutionTarget

END
```

```text
      ▼

             │
             ▼

             │
             ▼
```

# Y hay algo todavía más importante: activación ≠ ejecución

Una activación puede crear:

```text
Agent Run
Workflow Run
Deterministic Job
Human Task
Another Event
```

Por eso el router no debería necesariamente devolver `AgentId`.

Mejor:

```text
STRUCT ExecutionTarget
    type: ExecutionTargetType
    targetId: String
END
```

```text
ENUM ExecutionTargetType
    AGENT
    WORKFLOW
    JOB
    HUMAN_TASK
END
```

Esto mantiene la arquitectura empresarial mucho más general.

Un evento como:

```text
customer.invoice.overdue
```

podría producir:

```text
IF amount < $100
    → deterministic reminder workflow

ELSE IF amount < $10,000
    → collections agent

ELSE
    → human finance review
```

No todo necesita LLM.

Eso está perfectamente alineado con nuestra Constitution.

# Otro concepto importante: Event vs Activation

No son exactamente lo mismo.

Un evento declara:

```text
"Something happened."
```

Ejemplo:

```text
InvoicePaymentFailed
```

Una Activation dice:

```text
"This occurrence has been accepted
as a reason to execute something."
```

Por tanto:

```text
Domain Event
     ↓
Activation Rule
     ↓
ActivationRequest
     ↓
Admission
     ↓
Execution
```

Miles de eventos pueden existir sin activar ningún agente.

## Identity & Principal

Hasta ahora `ExecutionContext` tiene identidad, pero en enterprise esto debe crecer bastante.

Cada ejecución necesita responder:

```text
Who initiated this?
On whose behalf is it executing?
Which organization?
Which tenant?
Which roles?
Which permissions?
```

Por ejemplo:

```text
STRUCT Principal
    principalId: PrincipalId
    type: PrincipalType

    tenantId: TenantId

    roles: List<Role>
    permissions: PermissionSet

    delegatedBy: Optional<PrincipalId>
END
```

Y:

```text
ENUM PrincipalType
    HUMAN
    SERVICE
    AGENT
    WORKFLOW
    SYSTEM
END
```

Esto permite algo fundamental:

```text
Gabriel
   ↓ delegates
Finance Agent
   ↓
SAP
```

SAP no debería ver simplemente:

```text
agent-27
```

Debe existir una cadena verificable de autoridad:

```text
Human
 ↓
Agent
 ↓
Tool
 ↓
Enterprise System
```

Esa separación puede convertirse en una parte central de la **Architecture Constitution**, porque nos permite pasar de:

> “¿Cómo construyo un agente?”

Ahí es donde el harness deja de ser una librería y empieza a convertirse realmente en una **plataforma empresarial de ejecución de IA**.
