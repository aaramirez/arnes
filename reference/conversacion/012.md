Como se considera human in the loop sin tui

Sí. **Human-in-the-loop (HITL) no debería depender del TUI.** De hecho, arquitectónicamente sería un error hacerlo depender de la interfaz.

El TUI es solamente **uno de los canales mediante los cuales un humano puede responder**. HITL debería ser una capacidad del runtime.

Piensa en este caso:

```text
Agent
  ↓
Tool Call
  ↓
deploy_production()
  ↓
Policy Engine
  ↓
REQUIRES_APPROVAL
  ↓
Agent Run = WAITING_FOR_APPROVAL
```

En ese momento el agente puede incluso no tener ninguna interfaz abierta.

El runtime persiste algo como:

```ts
interface ApprovalRequest {
  id: string;
  runId: string;
  agentId: string;

  action: string;
  arguments: unknown;

  requestedAt: Date;
  requestedBy: string;

  status:
    | "pending"
    | "approved"
    | "rejected"
    | "expired";

  expiresAt?: Date;
}
```

La ejecución queda suspendida:

```text
AgentRun
   │
   ▼
RUNNING
   │
   ▼
Tool requires approval
   │
   ▼
WAITING_FOR_APPROVAL
   │
   ├───────────── potentially hours/days ─────────────┐
   │                                                  │
   │                                           Human decision
   │                                                  │
   ◄──────────────────────────────────────────────────┘
   │
   ├── APPROVED → RUNNING
   │
   └── REJECTED → RUNNING / TERMINATED
```

Aquí aparece una consecuencia arquitectónica importante: **el harness debe soportar ejecución durable**. No podemos tener un `await approval()` manteniendo un proceso Node abierto durante tres días.

En cambio:

```text
Agent State
+
Session State
+
Pending Operation
+
Approval Request
        ↓
     persist
```

y el proceso puede morir completamente.

Cuando llega la decisión:

```text
Human
  ↓
Approval API
  ↓
Approval Service
  ↓
resume(runId)
  ↓
restore checkpoint
  ↓
AgentLoop continues
```

### ¿Cómo llega la aprobación humana?

Ahí es donde aparecen los adapters:

```text
                    Approval Service
                          │
          ┌───────────────┼────────────────┐
          ▼               ▼                ▼
         TUI             Web              Slack
          │               │                │
       [Y/N]        [Approve][Deny]     Buttons

                          │
              ┌───────────┼───────────┐
              ▼           ▼           ▼
             Email      Mobile       Teams
```

Todos terminan llamando al mismo contrato:

```ts
approve(requestId, humanIdentity);
```

o:

```ts
reject(requestId, humanIdentity, reason);
```

Por eso **HITL pertenece al core/platform layer; la experiencia de aprobación pertenece al interface layer.**

Y no limitaría HITL a approvals. Hay por lo menos cuatro interacciones humanas importantes:

```text
APPROVAL
"¿Puedo ejecutar esta acción?"

INPUT
"Necesito información que no tengo."

REVIEW
"Preparé esto. Revísalo antes de continuar."

DECISION
"Tengo tres alternativas y necesito que
un humano seleccione una."
```

Por ejemplo, un agente de compras podría llegar a:

```text
Agent:
Encontré tres proveedores.

A: $80K — 14 días
B: $73K — 30 días
C: $91K — 7 días

Policy:
Purchases > $50K require procurement decision.

                ↓

HUMAN_DECISION_REQUIRED
```

El harness persiste:

```text
type HumanInteraction =
    | ApprovalRequest
    | InputRequest
    | ReviewRequest
    | DecisionRequest;
```

Esto me parece una abstracción mejor que llamar a todo `ApprovalService`.

Yo lo llamaría:

```text
Human Interaction Service
```

con:

```text
requestHumanInteraction()
resolveHumanInteraction()
cancelHumanInteraction()
expireHumanInteraction()
```

Y entonces tenemos algo bastante poderoso:

```text
                    AGENT LOOP
                        │
              ┌─────────┴──────────┐
              ▼                    ▼
        Autonomous            Human Required
         Execution             Interaction
              │                    │
              │                    ▼
              │             persist checkpoint
              │                    │
              │                    ▼
              │             WAITING_FOR_HUMAN
              │                    │
              │            ┌───────┼────────┐
              │            ▼       ▼        ▼
              │           TUI     Web      Slack
              │                    │
              │                    ▼
              │               Human response
              │                    │
              ◄────────────────────┘
                        │
                        ▼
                     resume
```

Esto además cambia algo de nuestra arquitectura anterior. Yo agregaría formalmente:

```text
Human Interaction
```

como componente independiente:

```text
Agent Harness
├── Agent Core
├── Model Gateway
├── Context Engine
├── Tool Runtime
├── Policy Engine
├── Session Manager
├── Human Interaction
├── Event Bus
├── Scheduler / Durable Execution
└── Interfaces
```

Y establecería otro **invariante arquitectónico**:

> **Ninguna interacción humana debe depender de una interfaz específica. Las interfaces transportan la interacción; el runtime define y persiste su significado.**

Eso permite que el mismo agente que hoy pide aprobación mediante TUI mañana pueda correr completamente unattended en Kubernetes y pedir la aprobación al gerente por Slack, Web, email o una aplicación móvil **sin modificar una línea del Agent Core**.
