Que tan difícil es extraer las rutinas asociadas al tui?

No parece demasiado difícil, porque Pi ya hizo la parte más importante: **el TUI está empaquetado como `@earendil-works/pi-tui` y el coding agent lo consume como dependencia separada**. ([GitHub][1])

Pero hay que distinguir dos cosas:

**Extraer `pi-tui` como librería reutilizable:** relativamente fácil. Ya existe como paquete independiente dentro del monorepo y está descrito como una librería de terminal UI con differential rendering. ([GitHub][2])

**Extraer “la experiencia visual completa de Pi” para usarla en nuestro harness:** dificultad media, porque parte de la UI concreta vive en `pi-coding-agent` y conoce conceptos propios del agente: sesiones, selección de modelos, tool rendering, mensajes, comandos, etc. Por ejemplo, hay archivos específicos como `tui-renderer.ts` y `model-selector.ts` dentro de `packages/coding-agent/src/tui/`. ([GitHub][3])

Yo lo visualizaría así:

```text
Pi

packages/tui
│
│  @earendil-works/pi-tui
│
├── Terminal abstraction
├── Renderer
├── Input handling
├── Components
├── Layout
├── Editor
└── ANSI/differential rendering

              ▲
              │ reusable
              │
packages/coding-agent
│
└── src/tui/
    ├── coding-agent renderer
    ├── model selector
    ├── session selector
    ├── tool displays
    ├── messages
    └── Pi-specific interactions
```

Por tanto, **yo no copiaría archivos individuales del TUI**. Haría algo más limpio: usar directamente `@earendil-works/pi-tui` como dependencia de nuestro proyecto, al menos inicialmente.

```json
{
  "dependencies": {
    "@earendil-works/pi-tui": "^0.82.1"
  }
}
```

La versión actual del paquete que aparece en el monorepo está alineada con `pi-coding-agent` `0.82.1`. ([GitHub][4])

Entonces nuestro proyecto podría tener:

```text
our-harness/
├── packages/
│   ├── ai/
│   ├── agent-core/
│   ├── tools/
│   └── tui/
│
└── apps/
    └── cli/
```

Y:

```text
our tui
   ↓
@earendil-works/pi-tui
   ↓
terminal
```

Mientras nuestro TUI escucha nuestros propios eventos:

```ts
agent.on("message_update", event => {
  ui.updateMessage(event);
});

agent.on("tool_execution_start", event => {
  ui.showTool(event);
});

agent.on("tool_execution_end", event => {
  ui.updateTool(event);
});
```

Eso nos deja usar **el motor TUI de Pi sin acoplarnos al coding agent de Pi**.

Además, hay una señal muy buena de que esto es intencional: las extensiones de Pi pueden importar `pi-tui` y construir UI propia. Incluso los ejemplos oficiales muestran extensiones con custom rendering, selectores, questionnaires y message renderers. ([GitHub][5])

### Lo que yo haría

No intentaría “extraer” el código todavía. **Lo consumiría como librería.**

Primero:

```text
@earendil-works/pi-tui
          ↓
    Our TUI Adapter
          ↓
      Our Events
          ↓
    Our Agent Core
```

Y mantendría una interfaz nuestra en el medio:

```ts
export interface HarnessUI {
  start(): Promise<void>;

  onAgentStart(): void;

  onMessageStart(id: string): void;
  onMessageUpdate(
    id: string,
    content: string
  ): void;

  onToolStart(
    id: string,
    tool: string,
    args: unknown
  ): void;

  onToolEnd(
    id: string,
    result: unknown
  ): void;

  onAgentEnd(): void;
}
```

Luego:

```ts
class PiTUIAdapter implements HarnessUI {
  // implementation using @earendil-works/pi-tui
}
```

Eso nos permite mañana cambiar:

```text
PiTUIAdapter
```

por:

```text
InkAdapter
WebSocketUIAdapter
ReactWebAdapter
VSCodeAdapter
```

sin modificar el core.

Y aquí aparece algo muy interesante para el proyecto: **podemos reutilizar `pi-tui` sin reutilizar `pi-agent-core`**.

Eso nos permitiría construir desde cero nuestro runtime enterprise y, sin gastar meses construyendo terminal UI, arrancar con una experiencia bastante cercana a Pi:

```text
                  OUR PROJECT

┌────────────────────────────────────┐
│          Enterprise Harness        │
│                                    │
│ Agent Loop                         │
│ Context                            │
│ Policies                           │
│ Tools                              │
│ Events                             │
│ Sessions                           │
└────────────────┬───────────────────┘
                 │ events
                 ▼
┌────────────────────────────────────┐
│          Our TUI Adapter           │
└────────────────┬───────────────────┘
                 │
                 ▼
┌────────────────────────────────────┐
│      @earendil-works/pi-tui        │
└────────────────────────────────────┘
```

**Yo escogería esta estrategia para v0.1.** Nos ahorra construir un renderer y al mismo tiempo evita que nuestro harness termine siendo un fork de Pi.
