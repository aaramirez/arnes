Para que el harness pueda evaluar el resultado del tool call y evaluar si debe seguir realizando nuevas llamadas o terminar 

Exacto. Y ahí está el corazón de un agente: **el harness no ejecuta una secuencia fija; ejecuta un ciclo de decisión**.

El resultado del tool call vuelve al modelo como una nueva observación:

```text
Modelo decide
   ↓
Tool call
   ↓
Harness ejecuta
   ↓
Tool result
   ↓
Modelo reevalúa
   ↓
¿seguir actuando o terminar?
```

Eso permite comportamientos como:

```text
1. Leer archivo
2. Detectar que falta contexto
3. Leer otro archivo
4. Encontrar el bug
5. Editar
6. Ejecutar tests
7. Ver que fallan
8. Corregir de nuevo
9. Ejecutar tests
10. Terminar
```

El harness controla **el ciclo y la ejecución**, mientras que el modelo controla **la siguiente decisión**.

La distinción importante es esta:

> **El modelo razona sobre la observación. El harness gobierna cómo esa observación se obtiene, se registra y se vuelve a introducir al ciclo.**

Y eso nos lleva al siguiente concepto clave de Pi: **el harness no debería confiar ciegamente en cualquier tool call que produzca el modelo**.

Antes de ejecutar puede haber una etapa así:

```text
tool_call
   ↓
validar schema
   ↓
validar tool existente
   ↓
beforeToolCall
   ↓
policy / permisos
   ↓
execute
   ↓
afterToolCall
   ↓
tool_result
```

Para nuestro harness enterprise, esta zona sería crítica.

Por ejemplo, el modelo pide:

```json
{
  "tool": "deploy",
  "environment": "production"
}
```

El modelo **no decide si tiene permiso** para hacerlo. Solo expresa la intención.

El harness decide:

```text
¿Existe deploy?
        ↓
¿Los argumentos son válidos?
        ↓
¿Este agente puede desplegar?
        ↓
¿Production requiere aprobación?
        ↓
¿Existe una aprobación válida?
        ↓
ejecutar / bloquear
```

Esa separación es fundamental:

```text
LLM = propone acciones

Harness = autoriza y ejecuta acciones
```
