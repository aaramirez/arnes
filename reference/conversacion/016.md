Como es la constitución completa?

La **Architecture Constitution** debería ser bastante más que los 15 principios. Yo la trataría como la **“ley fundamental” del harness**: cualquier componente, PR, extensión o decisión de arquitectura debería poder evaluarse contra ella.

La estructuraría en **11 artículos**.

## Preámbulo

> El harness existe para proporcionar una infraestructura segura, observable, extensible y agnóstica al modelo donde sistemas probabilísticos puedan razonar y proponer acciones, mientras mecanismos determinísticos gobiernan su ejecución.

La separación fundamental sería:

```text
Probabilistic Intelligence
        │
        │ proposes
        ▼
Deterministic Runtime
        │
        │ governs
        ▼
External World
```

El modelo puede decidir **qué intentar**.

El harness decide **qué puede ocurrir**.

---

# Artículo I — Principios fundamentales

Aquí viven nuestros **15 principios**:

1. **Context is a first-class architectural component.**
2. **The model is replaceable.**
3. **Tools are explicit capabilities, not prompt tricks.**
4. **Every action produces observable events.**
5. **Side effects pass through policy.**
6. **Agents are configuration over a shared runtime.**
7. **Skills encode reusable procedural knowledge.**
8. **Agent state and session state are different concerns.**
9. **Single-agent reliability precedes multi-agent complexity.**
10. **The harness owns execution state—not the model.**
11. **UI is an adapter, not part of the core.**
12. **Events observe; hooks intervene.**
13. **Authorization is deterministic and external to the LLM.**
14. **Context should be selected, not dumped.**
15. **Automation and agents should share the same execution substrate.**

Pero estos son principios de diseño. La Constitution necesita además reglas más estrictas.

# Artículo II — Invariantes

Un principio dice:

> “El modelo debe ser reemplazable.”

Un invariante dice:

> **“Ningún código dentro de AgentLoop puede depender de una API específica de OpenAI, Anthropic, Google u otro proveedor.”**

Eso ya es verificable.

Yo definiría inicialmente unos **20 invariantes**.

### Model

```text
INV-01
AgentCore nunca depende directamente
de un proveedor de modelos.

INV-02
Toda comunicación con modelos utiliza
el contrato interno AgentMessage.

INV-03
El modelo nunca constituye una
fuente de autorización.
```

### Tools

```text
INV-04
Todo ToolCall debe ser validado
antes de ejecutarse.

INV-05
Todo ToolCall pasa por ToolRuntime.

INV-06
Todo side effect pasa por PolicyEngine.

INV-07
Todo ToolResult vuelve al AgentLoop
como una observación explícita.
```

### Execution

```text
INV-08
Harness owns execution state.

INV-09
Todo AgentRun tiene límites explícitos.

INV-10
Todo AgentRun puede ser cancelado.

INV-11
Los side effects críticos deben soportar
idempotencia o deduplicación.
```

### State

```text
INV-12
AgentState y SessionState
son estructuras independientes.

INV-13
Una ejecución durable debe poder
reconstruirse desde estado persistido.
```

### Human interaction

```text
INV-14
Human Interaction nunca depende
de una interfaz particular.

INV-15
Una acción que requiere aprobación
no puede ejecutarse antes de recibirla.
```

### UI

```text
INV-16
AgentCore puede ejecutarse sin UI.

INV-17
UI consume eventos;
no controla internamente AgentLoop.
```

### Observability

```text
INV-18
Toda acción significativa produce
un evento observable.

INV-19
Toda decisión crítica debe ser trazable.

INV-20
Todo error debe pertenecer
a una categoría conocida.
```

Esto permite eventualmente crear **architecture tests** que comprueben parte de la Constitution automáticamente.

# Artículo III — Componentes soberanos

Aquí definimos qué componentes fundamentales existen y qué responsabilidad exclusiva tiene cada uno.

```text
Agent Runtime
│
├── AgentCore
├── AgentLoop
├── ModelGateway
├── ContextEngine
├── ToolRuntime
├── PolicyEngine
├── SessionManager
├── HumanInteractionService
├── EventBus
├── ExecutionController
└── CapabilityRegistry
```

Cada componente tiene un **decision boundary**.

Por ejemplo:

### AgentLoop

Responsable de:

```text
turn lifecycle
continuation
model → tool → observation cycle
completion
```

No responsable de:

```text
authorization
UI
database persistence
provider-specific APIs
```

### ContextEngine

Responsable de:

```text
selection
ranking
composition
compaction
context budgets
```

### PolicyEngine

Responsable de:

```text
allow
deny
require approval
constraints
```

Esto evita que aparezca un `AgentService.ts` de 8.000 líneas que termine controlando todo.

# Artículo IV — Decision Ownership

Este artículo responde una pregunta fundamental:

> **¿Quién tiene autoridad para decidir qué?**

```text
LLM
│
└── What should I try?

AgentLoop
│
└── Should another reasoning turn occur?

ContextEngine
│
└── What should the model know?

ModelGateway
│
└── How is the model invoked?

ToolRuntime
│
└── How is an action executed?

PolicyEngine
│
└── May this action occur?

HumanInteraction
│
└── Does execution require human input?

SessionManager
│
└── What execution history persists?

ExecutionController
│
└── May the run continue operationally?

UI
│
└── How is the state presented?
```

Esta matriz es importantísima porque previene responsabilidades duplicadas.

# Artículo V — Lifecycle

El harness debe tener una máquina de estados explícita.

```text
CREATED
   ↓
INITIALIZING
   ↓
RUNNING
   ↓
┌──────────────────────┐
│                      │
│ WAITING_FOR_MODEL    │
│ WAITING_FOR_TOOL     │
│ WAITING_FOR_HUMAN    │
│                      │
└──────────────────────┘
   ↓
RUNNING
   ↓
COMPLETED
```

Y estados alternativos:

```text
PAUSED
FAILED
CANCELLED
EXPIRED
```

Las transiciones deben estar definidas.

Por ejemplo:

```text
WAITING_FOR_HUMAN
        │
        ├── approved → RUNNING
        ├── rejected → RUNNING / FAILED
        ├── expired  → FAILED
        └── cancelled → CANCELLED
```

El LLM no controla esta máquina de estados.

# Artículo VI — Execution Constitution

Aquí establecemos cómo puede ejecutarse trabajo.

Todo tool call sigue:

```text
Tool Intent
     ↓
Resolve Capability
     ↓
Validate Schema
     ↓
beforeToolCall
     ↓
Policy Evaluation
     ↓
Authorization
     ↓
Human Approval?
     ↓
Execution Budget
     ↓
Sandbox
     ↓
Execute
     ↓
afterToolCall
     ↓
ToolResult
     ↓
Observation
```

No debería existir ningún camino alternativo como:

```ts
await shell.exec(command);
```

desde AgentLoop.

Todo pasa por el runtime.

# Artículo VII — Failure Constitution

Aquí definimos qué significa fallar.

Taxonomía:

```text
ValidationError
PolicyError
ToolError
ModelError
ContextError
HumanInteractionError
PersistenceError
InfrastructureError
BudgetExceeded
Cancellation
FatalError
```

Y cada error tiene propiedades:

```ts
interface HarnessError {
  category: ErrorCategory;

  recoverable: boolean;
  retryable: boolean;

  retryAfter?: number;

  cause?: Error;

  metadata?: unknown;
}
```

Entonces:

```text
HTTP 503
→ retryable

invalid arguments
→ recoverable by model

policy denied
→ not retryable

budget exceeded
→ stop

user cancelled
→ stop gracefully
```

El manejo de errores deja de ser improvisado.

        ↓

Teams

# Artículo IX — Resource Constitution

Aquí definimos límites.

Todo run debe tener un:

```text
ExecutionBudget
```

por ejemplo:

```ts
interface ExecutionBudget {
  maxTurns: number;
  maxToolCalls: number;

  maxInputTokens: number;
  maxOutputTokens: number;

  maxCost: number;
  maxRuntimeMs: number;

  maxConcurrentTools: number;
}
```

Y el harness controla:

```text
AgentLoop
   │
   ▼
ExecutionController
   │
   ├── turns?
   ├── tokens?
   ├── cost?
   ├── runtime?
   └── tool calls?
```

El modelo no puede decidir ignorar estos límites.

# Artículo X — Observability Constitution

Todo `AgentRun` debe generar una historia reconstruible.

```text
AgentRun
│
├── run_started
├── context_built
├── model_requested
├── model_response
├── tool_requested
├── policy_evaluated
├── tool_started
├── tool_completed
├── human_requested
├── human_resolved
├── turn_completed
└── run_completed
```

Y cada evento debería contener como mínimo:

```text
eventId
timestamp
runId
sessionId
agentId
traceId
eventType
payload
```

Así podemos construir posteriormente:

```text
Logs
Tracing
Audit
Replay
Analytics
Evals
Cost Analysis
Debugging
```

sobre la misma fuente de eventos.

# Artículo XI — Evolution Constitution

Este último artículo regula **cómo puede evolucionar el harness**.

Yo pondría reglas fuertes:

> **EVO-01 — El core debe permanecer pequeño.**

Una nueva funcionalidad debe intentar implementarse primero mediante:

```text
Extension
Hook
ContextProvider
Tool
Policy
Event Consumer
Adapter
```

antes de modificar AgentCore.

> **EVO-02 — No introducir multi-agent para resolver problemas que pueden resolverse mejor con tools o workflows.**

> **EVO-03 — No usar prompts para implementar controles que pueden ser determinísticos.**

Por ejemplo, nunca:

```text
"Please don't deploy to production
unless the user has permission."
```

como mecanismo de seguridad.

Debe ser:

```text
PolicyEngine
```

> **EVO-04 — Toda nueva integración debe declarar sus side effects.**

> **EVO-05 — Todo componente nuevo debe definir failure semantics.**

> **EVO-06 — Todo componente nuevo debe ser observable.**

> **EVO-07 — Toda nueva dependencia del core requiere justificación arquitectónica.**

> **EVO-08 — Breaking changes a contratos fundamentales requieren Architecture Decision Record.**

# Y agregaría un Artículo XII

Aunque originalmente hablábamos de 11, después de todo lo que hemos discutido creo que falta uno particularmente importante:

## Artículo XII — Deterministic vs Agentic Boundary

Esta podría convertirse en una de las ideas más importantes de todo nuestro harness.

Debemos definir explícitamente qué decisiones pertenecen al modelo y cuáles **nunca** deben pertenecer al modelo.

### Agentic

El LLM puede decidir:

```text
interpret intent

form hypothesis

decide what information is missing

select appropriate capability

analyze observations

propose next semantic action

determine whether the user's
semantic objective appears satisfied
```

### Deterministic

El runtime decide:

```text
authorization

schema validation

identity

permissions

budgets

timeouts

retries

idempotency

sandboxing

rate limits

approval requirements

state transitions

audit requirements
```

La frontera sería:

```text
                PROBABILISTIC

                    LLM
                     │
               proposes intent
                     │
                     ▼
════════════════════════════════════
        DETERMINISTIC BOUNDARY
════════════════════════════════════
                     │
                     ▼
              Harness Runtime
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
      Policy       State       Execution
        │            │            │
        └────────────┼────────────┘
                     ▼
                Real World
```

Y formularía probablemente la **regla constitucional principal** de todo el proyecto así:

> **Probabilistic systems may propose decisions. Deterministic systems must govern consequences.**

Eso resume casi todo lo que estamos construyendo.

Por eso yo ya no llamaría a esta sección simplemente “Architecture Principles”. La llamaría formalmente **Agent Harness Architecture Constitution**, versionada como código —por ejemplo `ARCHITECTURE_CONSTITUTION.md`— y cualquier cambio importante del harness tendría que demostrar que sigue cumpliéndola.
